# 《海上探险家》V2：本地存档耐久性与物理损坏恢复（迭代 1）

日期：2026-07-17

候选范围：iOS 2.0.0（build 1），V2 第一章本地存档

本轮结论：**底层存档容器已从“直接覆盖且信任文件头”改为“容量受限编解码、原子替换、旧档兼容、物理损坏可见恢复”；`V2-020 / P0` 已在仓库内关闭。模拟器已实际把有效存档截断为 7 字节，Release 构建重新启动后没有崩溃，自动生成合法新档并向玩家显示恢复说明。**

## 1. 为什么此前的恢复测试不够

既有 `V2-010` 修复验证了 JSON 已经成功读取以后，`resources`、`ship`、`battle` 等嵌套字段损坏时能回退到合法状态。但底层 `Record` 容器在 Lua 之前执行，原实现存在另一层风险：

1. 保存时用 `fopen(..., "wb")` 直接截断正式文件；若进程在写入中断，旧档和新档都可能丢失；
2. 文件头中的整数宽度、原文长度和压缩长度未经边界校验就参与 `memcpy`、分配与解压；
3. 压缩输出缓冲区只按原文长度分配，但 LZSS 对低重复数据可能因为标记字节而比原文更大；
4. 解压器不知道输出缓冲区容量，恶意或随机损坏的回溯引用可能先越界写入，事后长度比较来不及保护；
5. LZSS 构造函数使用数组分配，析构却使用标量 `delete`，属于未定义行为；
6. 原生缓存插入条件反写，既没有可靠缓存首个值，也不能正确替换旧值。

因此“Lua 损坏档测试通过”不能证明物理文件截断、错误文件头或压缩流损坏不会在启动时崩溃。按现有测试协议，启动崩溃或存档损坏属于 P0，本轮登记 `V2-020` 后优先处理。

## 2. 新的存档边界

### 2.1 兼容编解码器

新增 `RecordCodec`，保留历史磁盘格式和异或混淆周期，不强迫现有玩家清档。读取时先验证：

- 文件不为空且总长度不超过编码上限；
- 历史整数宽度只能是 4 或 8 字节，且不能超过当前平台可表示宽度；
- 头部必须完整；
- 解压后长度大于 0 且不超过 16 MiB；
- 压缩长度必须大于 0，且与文件剩余字节精确相等；
- LZSS 输出不得超过文件头声明的原文容量；
- 实际解压长度必须与声明长度相等；
- 作为字符串存档的内容不能包含内嵌 NUL。

16 MiB 上限远高于当前约 2 KiB 的 V2 JSON 状态，同时阻止损坏头部触发异常大分配。若未来存档结构确实需要更大容量，应通过版本化评审调整，不能让文件自行声明无限大小。

### 2.2 受限 LZSS

LZSS 内存输出现在接收明确容量，并记录 `OutputOverflow`。写满容量后不再移动输出指针，调用方把该容器判为无效。压缩侧使用“原文 + 每 8 字节一个标记 + 最终缓冲余量”的安全上界，不再把压缩结果写入等长缓冲区。

四个内部数组的析构全部改为 `delete[]`，输入计数也不再在 EOF 判断失败时继续递增。

### 2.3 原子保存

正式文件不再直接打开覆盖。新流程为：

1. 在同目录写入 `<save>.tmp`；
2. 检查完整 `fwrite`；
3. `fflush` 并在 Apple/POSIX 平台执行 `fsync`；
4. 关闭文件；
5. 用同目录 `rename` 原子替换正式文件；
6. 只有替换成功后才失效内存缓存。

任何编码、临时文件、写入、刷盘、关闭或替换失败都会保留上一份正式存档。遗留 `.tmp` 文件在下次写入时会被覆盖，不会被读取为正式状态。

### 2.4 玩家可见恢复

`SaveDataManager:loadData` 现在先记录物理文件是否存在：

- 新安装没有文件且读取为 `nil`：正常创建新档，不显示错误；
- 物理文件存在但原生容器返回 `nil`：标记 `containerLoadFailed`；
- V2 控制器使用与 JSON 损坏相同的 `SAVE_RECOVERY_MESSAGE` 创建合法新档；
- 玩家在“当前目标”和“最近结果”中看到存档已安全恢复，而不是静默重置或卡在加载页。

## 3. 兼容性验证

本轮同时验证两类旧档：

- 自动构造 4 字节长度头的历史 32 位容器，能够被当前 64 位编解码器读取，正文逐字一致；
- 从 iPhone 17 Pro Max 模拟器中读取本轮修改前生成的真实 1082 字节 V2 存档，新编解码器成功解出 1876 字节 JSON，并确认 `chapter_id = chapter_01`。

新写入仍使用当前平台历史布局，因此不改变 Lua schema、命名空间或用户进度语义。

## 4. 原生自动测试

`tools/release/test_record_codec.sh` 使用独立 C++ 测试程序，并同时启用 AddressSanitizer 与 UndefinedBehaviorSanitizer。每次发行回归覆盖：

- 正常 V2 JSON 往返；
- 256 KiB 低重复文本，验证压缩上界；
- 空文本和内嵌 NUL 拒绝；
- 一个合法容器的全部截断前缀；
- 非法整数宽度、超大原文长度和压缩长度不一致；
- 三字节压缩流试图向一字节输出区展开的越界场景；
- 32 位旧头兼容；
- 1500 组确定性多字节变异，不崩溃且任何被接受结果都受容量上限约束；
- 原子首次写入、完整替换；
- 人为阻止临时文件创建时返回失败，并确认上一份正式文件逐字节保留。

该测试已经接入 `tools/release/validate_ios_release.sh`，不依赖模拟器或用户目录。

## 5. iOS 运行验收

使用 `NewPirate Fresh QA` / iOS 26.2 专用模拟器和本轮 Release arm64 产物执行：

1. 卸载旧 App，干净安装并启动，生成 979 字节合法玩家存档；
2. 终止 App，备份后把 `v2_chapter_01_player_v2ChapterState` 截断为 7 字节；
3. 重新启动 Release App，等待超过 8 秒；
4. App 保持运行并进入“序章 · 瓶中召唤”；
5. 页面显示“存档已安全恢复，可以重新开始第一章”；
6. “最近结果”显示“检测到损坏或不兼容的存档，已安全创建新的首章航程”；
7. 原 7 字节文件已被新的 995 字节合法容器原子替换，玩家可以继续点击“握住水晶瓶”。

运行截图：[`save-container-recovery-player.png`](save-container-recovery-player.png)

这项证据证明物理截断会进入恢复路径，不只是在纯 Lua 测试里构造错误 table。

## 6. 静态门禁

发行静态校验新增以下不变量：

- `RecordCodec.cpp` 同时进入 iOS 与 macOS source phase；
- `Record` 必须经过 `encode`、`writeFileAtomically`、`readFile` 和 `decode`；
- 编解码器必须保留 4/8 字节头验证、总长度相等、容量上限、`fsync` 和 `rename`；
- LZSS 必须保留输出容量、溢出状态和数组析构修复；
- Lua 必须区分新安装与已有容器读取失败，并向 V2 控制器传递恢复状态；
- ASan/UBSan 原生测试必须继续存在并由发行脚本调用。

## 9. 仍然不由本轮替代的证据

- 模拟器物理截断不能替代签名真机上的强退、电量耗尽、系统回收和存储空间不足测试；
- 当前仍是本地单设备存档，没有账号、iCloud 或跨设备恢复；
- 删除并重装仍会按隐私/支持文案所述清除本地进度；
- 真机矩阵、两轮外部用户测试、Distribution 签名、TestFlight 和 App Store Connect 门槛继续保持未完成。

本轮关闭的是仓库内部可证明的“存档容器崩溃/非原子覆盖”风险，不会把总体上线状态误改为 GO。
